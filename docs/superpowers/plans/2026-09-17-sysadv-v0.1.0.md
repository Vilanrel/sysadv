# SysADV v0.1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir a fundação segura, auditável e multi-organização do SysADV v0.1.0 com autenticação, RBAC, processos, documentos, evidências, auditoria e interface web protegida.

**Architecture:** Monorepo TypeScript com React/Vite no frontend, Fastify no backend, PostgreSQL via Prisma e contratos compartilhados em Zod. A API é a autoridade para autenticação/autorização e isolamento por organização; documentos ficam fora da raiz pública e todas as operações críticas geram eventos de auditoria.

**Tech Stack:** React, TypeScript, Vite, React Router, React Hook Form, Zod, TanStack Query, Node.js, Fastify, Prisma, PostgreSQL, Vitest, Testing Library, Playwright, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-09-17-sysadv-v0.1.0-design.md`

## Global Constraints

- Frontend: React, TypeScript, Vite, React Router, React Hook Form, Zod, TanStack Query.
- Backend: Node.js, TypeScript, API REST, Fastify, Zod e OpenAPI.
- Persistência: PostgreSQL com Prisma.
- Infraestrutura: Docker Compose com `sysadv-web`, `sysadv-api`, `sysadv-postgres`, volumes persistentes e configuração por variáveis de ambiente.
- Senhas armazenadas exclusivamente como hash Argon2id.
- Access Token de curta duração e Refresh Token rotativo, com refresh token persistido de forma protegida/hashed e revogação de sessão.
- Cookies, quando usados: HttpOnly, Secure em produção, SameSite apropriado e proteção contra CSRF.
- Perfis iniciais: Administrador, Advogado, Calculista e Consulta.
- API é a autoridade final de autorização.
- Toda informação relevante ao cálculo deve manter origem e histórico.
- Divergências não podem ser resolvidas silenciosamente.
- Segregação por organização, escritório e processo é obrigatória.
- Uploads devem validar MIME/extensão, limitar tamanho, gerar SHA-256, usar nome interno e armazenar fora da raiz pública.
- Logs nunca podem armazenar senha, token completo ou segredo.
- Fora do escopo: IA jurídica completa, OCR produtivo, PJe-Calc produtivo, integração universal PJe/TRT, memória completa de cálculo e geração definitiva de `.pjc`.

- [ ] **Step 3: Implement password hashing and session rotation**

Use `argon2.hash(password, { type: argon2.argon2id })` and `argon2.verify`.
Generate cryptographically random refresh token with `randomBytes(48).toString('base64url')`; store only `sha256(refreshToken)` in `Session.refreshTokenHash`.
Issue short-lived signed access token containing only identifiers and authorization context.
Track failed attempts and temporary lockout in persistent user security fields or dedicated auth-attempt store; never return whether a user exists.

- [ ] **Step 4: Implement routes and cookies**

`POST /auth/login` validates Zod input, applies IP/identity rate limit, returns generic 401 on failure and writes the refresh token into HttpOnly cookie with `secure: env.NODE_ENV === 'production'` and SameSite configuration.
`POST /auth/refresh` rotates the session.
`POST /auth/logout` revokes current session and clears cookie.
`GET /auth/me` requires authentication.
